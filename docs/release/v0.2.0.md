# resolve-lang v0.2.0 — Name Resolution over HIR

**The foundation.** v0.2.0 turns the scaffold into a resolver: every path and
bare-identifier pattern of a `hir-lang` program is bound to the binder or
definition it names, under a language's scoping policy, across units and
imports. What does not resolve becomes a diagnostic, with a did-you-mean
suggestion where a visible name is close. The resolved program comes back as a
valid `Hir`, and a persistent index of definitions and references answers what
an editor asks: go to definition, find references, rename, outline.

## What is resolve-lang?

The semantic-analysis-tier crate of the `-lang` family that owns name
resolution. Every language LexerSketch forges lowers to HIR, so one resolver
serves all of them: the differences between PHP, Python, and Kraken scoping are
a `Policy`, not separate code. It depends on `hir-lang` (the representation it
resolves) and `intern-lang` (to compare spellings for suggestions), and nothing
else.

## What's new in 0.2.0

### The lazy path

```rust
use hir_lang::{Builder, Name};
use intern_lang::Interner;

let mut names = Interner::new();
let mut b = Builder::new();
let typo = b.name_expr(Name::new(names.intern("lenght")));
let body = b.block(&[], Some(typo));
let length = b.func(Name::new(names.intern("length")), &[], body);
let root = b.module(None, &[length]);

let res = resolve_lang::resolve(b.finish(root)?, &names)?;
assert_eq!(
    res.diagnostics()[0].message(&names),
    "cannot find value `lenght` in this scope; did you mean `length`?",
);
# Ok::<(), Box<dyn std::error::Error>>(())
```

### Policies

`Policy` captures a language's scoping as data: when items become visible
(whole scope, from the declaration, or the whole module wherever declared, as
PHP functions are), which namespaces exist and which share a table (Python keeps
one), whether binders may shadow, what duplicate definitions mean, what a class
body shows its methods (Kraken: everything; Python: nothing; PHP: only through
`self::`), whether nested modules see outer names, whether `self::`, `parent::`,
and `static::` bind early or late (PHP's late static binding), visibility, and
import forms and re-export. `Policy::kraken()`, `php()`, and `python()` are
presets; every setting has a `with_*` setter.

### Lexical resolution without re-deriving scopes

Binders come from hir-lang's own `lookup_local` and the walk's `Bind`, `Scope`,
and `Frame` events. Items, imports, and glob imports live on per-name shadow
stacks the walk pushes and pops, so the innermost visible item is found in
constant time per namespace, and a binder and an item compete by scope depth and
position. A local behind a frame it cannot cross is reported (`CannotCapture`),
not skipped in favour of an outer name.

### Imports as a least fixpoint

All imports of all units are resolved together. Each (scope, namespace, name)
slot only moves from absent to one binding to ambiguous; named imports copy the
slot their path reaches, globs join every visible slot of their target. Because
every rule is monotone, the result does not depend on declaration order —
property tests check this against a naive fixpoint on random module graphs, and
check that permuting modules changes nothing. Cycles across modules and units
resolve; import cycles, broken imports, and ambiguous globs are reported where
they matter.

### Multi-unit programs and the environment

`Program` resolves several units against each other; a unit given a root name
is reachable from every unit, and definitions of other units are `Res::Def` with
their `UnitId`. Everything outside the program — other packages, the standard
library, primitive types — comes from an `Env` the host implements, or the
in-memory `MapEnv`.

### Classes and mixins

HIR leaves mixin uses (PHP traits) for resolve-lang to expand. Each class gets an
effective member table with `insteadof` exclusions, `as` aliases and visibility
changes, and mixins of mixins expanded first; conflicts and cycles are reported.
`self::x`, `parent::x`, and `Class::x` look members up through the inheritance
chain, memoized along single-base chains, with private and protected access.

### The index

`Index` lists every definition (items, variants, binders, aliased imports, and
outside symbols that are referenced) and every reference per path segment.
Lookups are dense: `references` is an allocation-free iterator in location
order, `resolve_at` goes from a HIR path segment to its definition, `at` from a
source offset. `rename_set` includes import paths and leaves alone the uses that
went through an alias; names produced by expansions are listed separately.
`document_symbols` gives the outline.

## Guarantees and how they are checked

- Lexical resolution matches a reference scope-stack resolver on random programs
  of nested blocks, items, closures, and parameters, under scope hoisting and
  declare-before-use.
- Import resolution matches a naive least fixpoint on random module graphs with
  aliases, globs, public and private imports, cycles, and ambiguity, and is
  independent of module order.
- Every reference ends resolved, or with exactly one diagnostic; the result is a
  valid `Hir`; the index is consistent.
- No recursion over input: 100,000 nested blocks, 25,000 nested closures, and
  20,000 nested classes are tested.
- Glob propagation, inheritance walks, and suggestions run against an explicit
  `Budget`.

## Performance

Library numbers, measured with Criterion on a desktop x86_64 machine (Windows,
release profile), resolution including indexing and writing the `Hir`:

| Benchmark | Size | Time |
|---|---|---|
| One unit | 124,000 nodes | 24.6 ms |
| One unit | 1,240,000 nodes | 317 ms |
| 1,000 modules in a glob ring | 53,000 nodes | 19.9 ms |
| Eight units | 992,000 nodes | 263 ms |

## Not in this release

- Incremental update hooks (v0.5.0).
- `symbol-lang` and `module-lang` are not wired: their 1.x APIs do not fit
  (LexerSketch ISSUES M37, M38); revisited with their 2.0 APIs.
- No `diag-lang` conversion of diagnostics yet.
