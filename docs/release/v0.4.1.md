# resolve-lang v0.4.1 — PHP classes

**Mox's `new Foo` resolves.** v0.4.1 closes the three resolve-lang gaps that
bcgen-lang 0.4 found while compiling Mox classes: a class name in value
position (the Mox sketch's `new_object` template writes `mox.new(Foo, ...)`,
which resolve-lang 0.4 rejected as "expected a value, found class"), an
interface constant reached through an implementing class, and trait member
tables that differed from PHP. It is an additive patch: no public item changed
shape, and the two new `Policy` settings are on in `Policy::php()` and off in
every other preset.

## What is resolve-lang?

The semantic-analysis-tier crate of the `-lang` family that owns name
resolution. Every language LexerSketch forges lowers to HIR, so one resolver
serves all of them: the differences between PHP, Python, and Kraken scoping are
a `Policy`, not separate code. It depends on `hir-lang` (the representation it
resolves) and `intern-lang` (to spell and fold names), and nothing else.

## What's new in 0.4.1

### A class name in value position

```rust
use hir_lang::{ClassDef, Expr, Item, ItemKind, Name, Ns, Res, Vis};
use intern_lang::Interner;
use resolve_lang::{Policy, Resolver};

// class Foo {}      main() { mox.new(Foo) }
let mut names = Interner::new();
let mut b = hir_lang::Builder::new();
let foo_name = Name::new(names.intern("Foo"));
let foo = b.item(Item::new(Some(foo_name), ItemKind::Class(ClassDef::default())).with_vis(Vis::Public));
let new_sym = names.intern("mox.new");
let new_path = b.resolved_path(Name::new(new_sym), Ns::Value, Res::Extern(new_sym));
let callee = b.expr(Expr::Path(new_path));
let operand = b.name_expr(foo_name); // the class, as the template writes it
let call = b.call(callee, &[operand]);
let body = b.block(&[], Some(call));
let main = b.func(Name::new(names.intern("main")), &[], body);
let root = b.module(None, &[foo, main]);
let hir = b.finish(root)?;
let unit = hir.unit();

let res = Resolver::new(Policy::php()).resolve(hir, &names)?;
assert!(res.is_clean());
let hir = res.hir(unit).unwrap();
let Expr::Path(p) = *hir.expr(operand) else { unreachable!() };
// The whole path is the class item, nothing left over: what bcgen-lang's
// class operations read.
assert_eq!(hir.path(p).res, Res::Def(hir.def(hir_lang::Def::Item(foo))));
assert_eq!(hir.path(p).unresolved, 0);
# Ok::<(), Box<dyn std::error::Error>>(())
```

`Policy::with_class_values(true)` (on in `Policy::php()`) makes a value path
that finds nothing in the value and constant tables fall back to the type
table, and resolve to a class there. It covers unqualified, module-qualified
(`App\Foo`, `\App\Foo`), and imported names, folded by the type table's case
rule (`new foo` finds `Foo`), and classes the host defines through the `Env`.

- A constant or function of the same name wins: the value tables come first.
- A callee does not fall back: `Foo()` is not `new Foo`, and keeps its
  "expected a value, found class" diagnostic.
- An interface (or a sum) stays an error in value position. hir-lang refuses a
  value path that resolves to one, which is why bcgen-lang takes interfaces as a
  type argument (`mox.instanceof<I>(x)`). Naming one in value position needs
  HIR support (it is on bcgen-lang's list for HIR).
- `Foo::class`, `Foo::bar()`, and `Foo::C` already worked: `Foo` is looked up as
  a container. `Foo::class` ends as the class with one segment left over, which
  is the other shape bcgen-lang reads; a test pins it.

### An interface constant through an implementing class

```rust
use resolve_lang::Policy;

// interface I { const X = 1; }   class Impl implements I {}   Impl::X
// resolves to I's X: the class and its base classes first, then its
// interfaces, nearest class first, each with its super-interfaces.
assert!(Policy::php().interface_members());
assert!(!Policy::kraken().interface_members());
```

`Impl::X` used to stay type-directed (`Res::Def(Impl)` with one segment left);
under `Policy::php()` it now resolves to the interface's constant, as do
`self::X` inside `Impl`, `Child::X` for a subclass, and the constant of a
super-interface. A class's own constant still overrides the interface's (PHP
8.1). An abstract class reaches the interface's methods the same way. Lookups
are memoized per class and name and charged to the member-step budget; a
50,000-deep interface chain, a 20,000-deep class chain, and a class implementing
600 interfaces under a small budget are tests.

### Trait member tables follow PHP

bcgen-lang's `tests/mixins.rs` compares resolve-lang's member tables with a
model of PHP 8's `zend_traits_copy_functions` and `zend_add_trait_method`, and
counted 16 differing members in its 200 random programs. The same model now
agrees on 20,000 programs, and resolve-lang carries it itself
(`tests/php_mixins.rs`, 1,500 random mixin graphs per run, with abstract methods
added). The bugs:

- A visibility-only `as` rule on a method an `insteadof` rule excluded brought
  the excluded method back (PHP applies the rule to the copy, and there is none).
- An `as` alias replaced a member of that name from an earlier mixin; PHP keeps
  the first and reports the collision.
- `insteadof` and `as` rules matched constants and properties as well as
  methods.
- Abstract mixin methods could hide concrete ones.
- A function reaching a class twice at different visibilities was not a
  conflict.

### Checked against the consumer

Nothing was edited in bcgen-lang. With this resolve-lang patched into a local
copy of it, its 15 class programs pass with every `new` and `instanceof` class
operand left for the resolver to resolve (they pass operands pre-resolved
today), and `tests/mixins.rs` reports 0 differences over 20,000 seeds.

## Performance

The paths that existed in 0.4.0 are untouched: new work happens only when a
lookup would otherwise fail (a value path that found nothing, a member the
class chain does not have). Existing benchmarks, run alternately on the old and
new code on the same loaded machine, differ by less than their own noise
(`resolve_php` 291 ms before, 284-289 ms after, 1.24M nodes; `resolve_classes`
131 ms before, 120-131 ms after, 219k nodes). The new benchmark
`resolve_php_classes` builds a 10,000-class PHP unit (chains of 50 classes, 400
interfaces in chains of four, 200 traits, class names as `mox.new` operands, an
interface constant read through every class, trait rules on every fifth
class): 245k nodes in about 180-220 ms (1.1-1.3 million nodes per second,
library only, loaded machine). With both new settings off the same unit takes
about 160 ms, so the new lookups cost on the order of 10-15% on a program that
is nothing but those lookups.

## Behavior changes under `Policy::php()`

The API only grows, but resolution under `Policy::php()` changes in the three
places above: class names in value position resolve (they were errors),
interface constants resolve (they were left unresolved), and a mixin table that
relied on a bug now has PHP's contents, with a `MixinConflict` where PHP would
report a collision. To keep 0.4.0's resolution, turn the two new settings off:

```rust
use resolve_lang::Policy;

let as_0_4_0 = Policy::php().with_class_values(false).with_interface_members(false);
assert!(!as_0_4_0.class_values() && !as_0_4_0.interface_members());
```

The mixin fixes have no switch. Other presets are unchanged.

## Not in this release

- A function or constant named like a class wins over the class in value
  position: the resolver cannot tell the operand of `new` from another value.
- Ambiguous inherited constants (PHP: "inherits both A::X and B::X") are not
  reported, and `ResolvedUnit::members` does not list inherited interface
  members.
- Mixin `final`, abstract-signature compatibility, and PHP 8.2 trait constant
  conflict rules are not modelled.
- Incremental update hooks (v0.5.0); the 0.3 leniencies and gaps stand.
