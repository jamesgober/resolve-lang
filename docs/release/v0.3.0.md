# resolve-lang v0.3.0 — PHP and Python Name Semantics

**The flagship semantics.** v0.3.0 closes what LexerSketch's ISSUES ledger
lists as P14: the name-resolution behaviour PHP (and so Mox) and Python (and so
Mercury) need before the Mox Demo milestone. Function, method, and class names
fold case as PHP 8 does; PHP's constants live in a table of their own; several
bases follow Python's C3 method resolution order; unqualified names inside a
class see what it inherits; and the import corner the 0.2 release notes called
lightly tested is now held to a differential test, which found three ordering
bugs, all fixed here.

## What is resolve-lang?

The semantic-analysis-tier crate of the `-lang` family that owns name
resolution. Every language LexerSketch forges lowers to HIR, so one resolver
serves all of them: the differences between PHP, Python, and Kraken scoping are
a `Policy`, not separate code. It depends on `hir-lang` (the representation it
resolves) and `intern-lang` (to spell and fold names), and nothing else.

## What's new in 0.3.0

### Case folding per table

```rust
use hir_lang::{Builder, Name};
use intern_lang::Interner;
use resolve_lang::{Policy, Resolver};

// function strLen() {}   function main() { STRLEN(); }
let mut names = Interner::new();
let mut b = Builder::new();
let body = b.block(&[], None);
let f = b.func(Name::new(names.intern("strLen")), &[], body);
let callee = b.name_expr(Name::new(names.intern("STRLEN")));
let call = b.call(callee, &[]);
let main_body = b.block(&[], Some(call));
let main = b.func(Name::new(names.intern("main")), &[], main_body);
let root = b.module(None, &[f, main]);

let res = Resolver::new(Policy::php()).resolve(b.finish(root)?, &names)?;
assert!(res.is_clean());
# Ok::<(), Box<dyn std::error::Error>>(())
```

`Case` (`Sensitive`, `AsciiInsensitive`) is set per table with
`Policy::with_case`. Every lookup goes through the table's key: unqualified
names, module paths, imports, class members, mixin rules, unit roots, and
duplicate detection. Folding is ASCII only, exactly PHP 8's rule; Unicode case
folding is deliberately not offered (no target language needs it, and its
tables change with the Unicode version). Names stay as written in diagnostics,
class members, and the index, and a rename covers references spelled in any
case. The fold maps each symbol to a canonical symbol fixed by the interner, so
results do not depend on visiting order.

### PHP's constant table

`Namespace::Const` holds constants. Every preset but `php` merges it into the
value table, so nothing changes there. `Policy::php()` keeps it apart and
case-sensitive, with globals and static properties beside the constants:

| Table | Holds | Case |
|---|---|---|
| value | functions, methods | ASCII-insensitive |
| type (with module) | classes, interfaces, traits, enums, namespaces | ASCII-insensitive |
| constant | constants, class constants, globals, static properties | sensitive |

So a method and a class constant of one name are no longer duplicates. A call's
callee searches functions first and any other value path constants first:
`self::size()` is the method, `self::size` the constant.

### C3 method resolution order

Several bases are linearized with C3 (Python's MRO), once per class, eagerly,
bases first, without recursion, and charged to the member budget. An
inconsistent hierarchy (`class Z(X, Y)` where `Y` derives from `X`, a repeated
base, contradictory orders) is reported as `DiagKind::InconsistentMro`, as
Python raises `TypeError` at class creation; member lookup then falls back to
the bases' orders concatenated without repeats, so it still answers.

### Inherited members in lexical class scopes

Under `ClassScope::Lexical` (Kraken, Java-style languages), an unqualified name
in a class body finds the class's own members, then inherited and mixin members
in method resolution order, then enclosing scopes. A base's private member is
not inherited, so the search goes on past it; the class header (bases,
interfaces, mixin uses) never sees inherited members, since it names them.

### The import corner

A relative import whose first segment is missing from its module while that
module's globs are still undetermined has to wait: a glob may yet provide the
name, which would shadow the enclosing scope. The new differential test
generates exactly these programs (relative imports, imports that bind modules,
globs carrying them, isolated and lexical module scoping) and compares them with
a naive fixpoint over per-table slots. It found three bugs:

1. When nothing could move, the lowest-numbered waiting import was settled in
   final mode even if it waited on another import, which then failed as an
   `ImportCycle` although that other import could still be settled through its
   fallback.
2. Final mode treated every glob-pending miss on the settled import's path as
   absent, including names a still-pending import could produce.
3. An import binding several tables kept the resolution of whichever table
   filled first.

Settling is now three-tiered: glob-blocked imports waiting on a name nothing
pending could produce are settled first, in an exact final mode; then other
glob-blocked imports in a forced final mode; only a true cycle of named imports
is broken in cycle mode. A multi-table import resolves to the first table in a
fixed order. Imports settled in a final mode are still rechecked and reported
as `ImportAmbiguity` if the finished tables disagree.

## Breaking changes

- `Namespace` gains `Const`; `Namespace::ALL` has six entries.
- `Policy::php()`: separate case-sensitive constant table, case-insensitive
  function/method/class/namespace tables, classes are types only.
- Several bases follow C3, not depth-first order; `DiagKind::InconsistentMro`
  is new (the enum is `#[non_exhaustive]`).
- Lexical class scopes see inherited members.
- `ClassMember::name` is the name as written.
- Multi-table imports resolve in a fixed table order.

## Guarantees and how they are checked

- PHP resolution matches a reference made of plain maps (functions by
  lowercased name, constants by exact name, first definition kept) on random
  programs of functions, constants, class members, `self::` and `Class::`
  paths, and calls spelled in random case; folding is invisible on all-lowercase
  programs.
- Member lookup and lexical inheritance match a textbook recursive C3 on random
  hierarchies (up to six classes, up to three bases, public, protected, and
  private members, deliberately inconsistent cases included) under the Kraken
  and Python policies; the number of `InconsistentMro` reports matches.
- Relative imports match a naive fixpoint over per-table slots on random module
  graphs where first segments arrive through globs or fall back to the
  enclosing module, under isolated and lexical scoping, with no
  `ImportAmbiguity` where the fixpoint is unique.
- Everything 0.2 guaranteed still holds: the existing differential tests pass
  unchanged.

## Performance

Library numbers, measured with Criterion on a desktop x86_64 machine (Windows,
release profile), resolution including indexing and writing the `Hir`:

| Benchmark | Size | Time |
|---|---|---|
| One unit | 124,000 nodes | 22.3 ms |
| One unit | 1,240,000 nodes | 219 ms |
| One unit under `Policy::php()`, every call through folding | 1,240,000 nodes | 215 ms |
| 1,000 modules in a glob ring | 53,000 nodes | 12.1 ms |
| Eight units | 992,000 nodes | 160 ms |
| 10,000 classes, three bases each, inherited members | 219,000 nodes | 97 ms |

Folding adds one pass over the interner when a policy has a case-insensitive
table, and nothing otherwise.

## Not in this release

- Incremental update hooks (v0.5.0).
- PHP leniencies kept on purpose: a bare function name resolves to the function
  when no constant exists, and a callee to a constant when no function exists.
- HIR paths carry no `$` sigil: static properties keep it in their names to stay
  apart from class constants.
- `symbol-lang` and `module-lang` remain unwired (ISSUES M37, M38); no
  `diag-lang` conversion yet.
